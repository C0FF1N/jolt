## Methodology

- **Harness:** `bench/src/run.mjs` (mock extension) and `bench/src/real-bench.mjs` (real Chromium). Both drive the built server over MCP stdio exactly like a client would, and time each `tools/call`.
- **Statistics:** median and p95 (nearest-rank) of per-iteration wall time; warm-up iterations discarded; cold start measured separately with fresh processes.
- **Setup is untimed:** page loads and ref lookups used to prepare a scenario are outside the measured region.
- **Fairness:** same machine, same Chromium, same extension build, same fixture pages, same iteration counts for baseline and turbo; each server runs in its own process on its own loopback port.
- **Round trips** are counted by the mock extension (messages received per iteration).

## Limitations (read before quoting any number)

- Single machine, single run set, not isolated from other processes; no confidence intervals. Differences under ~10% are within run-to-run noise.
- Repeated runs of the same code differed by up to about ±10% for individual standard-tool scenarios (e.g. `navigate` read 23.5, 22.8, 23.2 and 25.4 ms across four runs). Do not read a difference of that size in one scenario as an improvement or a regression.
- The `status` scenario calls `browser_get_console_logs`; its response bytes depend on whatever console output had accumulated in the tab, not on the server, so compare its latency only.
- Fixtures are small local pages served from loopback. Real sites add network and render time, which dominate and are identical for both servers; relative gains from fewer round trips shrink as per-action browser time grows.
- The Chromium here is Playwright's headless build, not branded Chrome, and the extension is this repo's reimplementation. **The original Web Store extension was not benchmarked** (loading it needs a manual Connect click in a profile where it is installed).
- The mock-extension numbers use a zero-latency extension and therefore exaggerate protocol overhead relative to real use; they are valid for round-trip counts, not as user-visible latency.
- Windows timer granularity (~15.6 ms for `setTimeout(1)`) makes a non-zero *simulated* extension delay unreliable; headline mock runs use 0 ms. `baseline-mock-rtt1-timer-quantized.json` is kept only as a documented example of this artefact.
- CPU and memory of the server process were not measured reliably in the real-browser runs (the mock runner records RSS only as a rough point sample); no claim is made about CPU or memory improvement.
- AI model latency and network conditions are out of scope; only tool execution time, payload bytes and call counts are measured.

## Reproduce

```bash
pnpm install && pnpm -r build
cd bench
node src/run.mjs --target=baseline --label=legacy --rtt=0 --iterations=40
node src/run.mjs --target=turbo --label=legacy --rtt=0 --iterations=40
node src/run.mjs --target=turbo --label=bundle --caps=snapshotBundle --rtt=0 --iterations=40
node src/real-bench.mjs --iterations=30 --warmup=5 --cold=5   # needs a Playwright Chromium (JOLT_BENCH_CHROME to override)
node src/report.mjs
```
